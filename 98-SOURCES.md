## Azure DevOps

| Reference | Why it matters |
|---|---|
| [Authentication guidance for integrations](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/authentication-guidance?view=azure-devops) | Prefer supported modern Microsoft Entra identity methods for Services; choose the appropriate authentication model for the integration/deployment |
| [Organization authentication guidance](https://learn.microsoft.com/en-us/azure/devops/organizations/security/authentication-guidance?view=azure-devops) | Interactive versus unattended identity and least-privilege approach |
| [Use personal access tokens](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/use-personal-access-tokens-to-authenticate?view=azure-devops) | A PAT is a secret, not a value to place in Markdown or GitHub; restrict use/scope/lifetime |
| [Get a work item, REST 7.1](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/work-items/get-work-item?view=azure-devops-rest-7.1) | Versioned work-item reads and expansion of relations; verify API version for the actual deployment |
| [Get query metadata](https://learn.microsoft.com/en-us/rest/api/azure/devops/wit/queries/get?view=azure-devops-rest-7.1) | Read query structure/scope rather than assuming a screenshot defines the whole backlog |
| [Use queries](https://learn.microsoft.com/en-us/azure/devops/boards/queries/using-queries?view=azure-devops) | Flat/tree/direct-link query behavior and saved-query context |
| [Dashboard widget catalog](https://learn.microsoft.com/en-us/azure/devops/report/dashboards/widget-catalog?view=azure-devops) | A dashboard can contain many widget types; story extraction depends on the actual widget/query |
| [Managed queries](https://learn.microsoft.com/en-us/azure/devops/boards/queries/about-managed-queries?view=azure-devops) | Query definitions and access vary by configuration |

For example, the documented Services work-item read pattern is `GET https://dev.azure.com/{organization}/{project}/_apis/wit/workitems/{id}?api-version=7.1`, with relation expansion where supported. This is a documentation pattern, not a real project endpoint or permission grant. Determine field mappings and relation semantics from the actual project/process. Do not copy legacy authentication snippets from an autogenerated REST security section instead of following current authentication guidance.

## Playwright

| Reference | Why it matters |
|---|---|
| [Locators](https://playwright.dev/docs/locators) | Use observed roles/labels/test IDs and supported locator semantics; no guessed DOM |
| [Electron API](https://playwright.dev/docs/api/class-electron) | Electron support is experimental; ordinary Playwright is not general native desktop automation |
| [Playwright API](https://playwright.dev/docs/api/class-playwright) | Actual API surface, including API request capabilities |
| [Test API](https://playwright.dev/docs/api/class-test) | Test context, fixtures and execution semantics |

| [Reporters](https://playwright.dev/docs/test-reporters) | Actual test outputs can feed reporting; a proposed reporter is not evidence of a run |

Attended headed walkthrough defaults in this library are presentation choices, not business requirements. `slowMo` helps observation and must not replace assertions/auto-waiting. Choose runtime and CI configuration according to the real project.
